  - 以路徑名稱查詢單一檔案（Python 3.12 起的 `os.lstat`、原生模組的 by-name 查詢）會對尚未被任何程式開啟過的一般檔案回報屬性 0x40000；同一個檔案的資料夾列舉與以控制代碼查詢都沒有這個位元。300 個樣本中，以控制代碼查詢過一次之後，路徑查詢就不再回報。Windows 文件記載 `FILE_ATTRIBUTE_RECALL_ON_OPEN`（0x40000）只出現在目錄列舉類別。
  - FileTree 把這個位元視為「資料在別處」，配置大小記為 0。`SysWOW64`：6,265 個檔案中 1,606 個被記為不佔空間（邏輯大小 511,184,608 位元組），純 Python 讀取與原生讀取都一樣，重複掃描結果相同。`System32`：4,048 個、5,245,408,896 位元組。Python 3.11（以控制代碼查詢）不受影響。
  - 只有這個位元的檔案，路徑查詢回報 0x40000，列舉與控制代碼查詢回報 0x80（NORMAL）。
- **修正**：
  - `core/snapshot.py` 新增 `path_metadata(info, listed_attributes=0)`：路徑中繼資料的 0x40000 位元一律改用資料夾列舉的值，沒有列舉時清除；清除後沒有其他屬性時記為 0x80。`stat_snapshot` 經過它。
  - `core/scanner.py`：`_entry_node` 以 `os.scandir` 項目的列舉屬性修正 `os.lstat` 的結果；交給 Python 處理的原生列（`_NamedEntry`）帶著原生模組回報的列舉位元。
  - `_native.cpp`：`read_folder` 以 `FindFirstFileExW` 的列舉屬性取代查詢結果中的這個位元（無法描述的項目也回報列舉位元）；`snapshot` 沒有列舉，一律清除。`core/native_scan.py` 的校準以同樣修正過的 `os.lstat` 比對。
  - `core/mft_scan.py`：路徑中繼資料以列舉屬性修正；連結數改為「非 DOS 命名空間的名稱紀錄數」必須等於 `st_nlink`，主紀錄沒有屬性清單時另外要求標頭連結數等於名稱紀錄數。量測依據：`C:\Windows` 前 4,707 個不一致的項目全部帶屬性清單，主紀錄標頭大於名稱紀錄數，延伸紀錄標頭為 0 或 16 位元負數，而 `st_nlink` 一律等於扣除別名後的名稱紀錄數。
- **修正後量測**：`SysWOW64` 在頂層仍有 1,475 個檔案被 `os.lstat` 回報該位元的情況下，兩種讀取的配置總量都是 1,402,949,632（修正前 889,016,320），樹與錯誤清單相同；`Microsoft.NET` 兩種讀取都是 641,216,512，等於 Python 3.11 的結果。MFT 稽核對 `System32`（30,901 個項目）的拒絕數由約兩成降為 967，其中 829 個屬於之後修正的「只剩 NORMAL」情況。

- **驗證**：所有引用掃描、快照、原生讀取或 MFT 稽核的測試檔（136 個檔案）在加入 NORMAL 規則前為 1,739 通過、28 略過；之後重建模組並重跑直接相關的 6 個測試檔，Python 3.14 為 81 通過、1 略過，Python 3.11（同一個 abi3 模組）50 通過、1 略過；`ruff check .` 通過。沒有跑整套。
